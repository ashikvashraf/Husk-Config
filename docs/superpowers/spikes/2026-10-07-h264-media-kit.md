# Spike: H.264 /screen.mp4 via media_kit (2026-10-07)

Question: Can media_kit play Husk's live fMP4 /screen.mp4 with acceptable latency?

## How this spike was run (and what it did not cover)

The plan's version of this spike (Steps 1-3: phone with screen sharing on, `flutter run -d macos -t lib/spike_h264_main.dart`, watched by a person) could not be run. The test phone `192.168.0.106:8090` is unreachable from the agent shell (`curl` exit 7), and agents cannot drive a GUI (Ruling R4).

What was run instead is a headless probe on macOS:
- **Player:** the libmpv that the macOS app bundles (`Husk Config.app/Contents/Frameworks/Mpv.framework`, mpv 0.36.0), loaded through Python ctypes with `vo=null`, `ao=null`. That is media_kit's own test-mode output.
- **Settings:** media_kit 1.2.6's NativePlayer init properties (`cache=yes`, `cache-on-disk=yes`, `hr-seek=yes`, `demuxer-max-bytes=32 MiB`, ...), then H264View's `profile=low-latency`, `cache=no` and `untimed=yes`.
- **Source:** a local stand-in for Husk's stream. ffmpeg encodes a live H.264 baseline stream at 720x1280, 30 fps, GOP 30, in real time (`-re`). It is served as fragmented MP4 (`frag_keyframe+empty_moov+default_base_moof`) over HTTP: `ffmpeg -re -f lavfi -i testsrc2=size=720x1280:rate=30 -c:v libx264 -preset ultrafast -tune zerolatency -profile:v baseline -g 30 -pix_fmt yuv420p -f mp4 -movflags frag_keyframe+empty_moov+default_base_moof -listen 1 http://127.0.0.1:PORT/screen.mp4`.
- **Sampling:** once per second, the probe logs `time-pos` (media_kit `state.position`), `demuxer-cache-time` (media_kit `state.buffer`, see media_kit-1.2.6 `real.dart:1544`) and wall-clock time minus `time-pos`. Three runs: (a) 23 s of plain playback; (b) a 5 s pause at t=6 s to simulate a stall, then resume; (c) the same as (b), plus a seek to `demuxer-cache-time` on resume.

**Not covered:**
- The phone's real stream (its encoder, resolution, network).
- media_kit_video's texture render path.
- End-to-end latency measured from a tap on the phone.
- Android, iOS and Windows.

## Results

| Platform | Plays? | Errors | Approx. latency | Drift over 60 s | Catch-up seek helps? |
|---|---|---|---|---|---|
| macOS | yes (headless libmpv, local stand-in stream) | none | ~0.05-0.2 s behind the live edge (stand-in stream, not phone end-to-end) | no (0.04 s at 1 s to 0.19 s at 23 s) | n.a.: the seek's `buffer - position > 2 s` trigger never occurs (see below) |
| Android | untested (no device reachable) | | | | |
| iOS | untested | | | | |
| Windows | untested | | | | |

### Catch-up seek

- With `cache=no`, mpv reads ahead at most `demuxer-readahead-secs`, which stays `1.000000` after `profile=low-latency`. The probe printed `cache = no`, `demuxer-readahead-secs = 1.000000` and `demuxer-lavf-o = fflags=+nobuffer`.
- **Plain playback (a):** `demuxer-cache-time - time-pos` was 0.00 at every sample.
- **5 s stall (b):** the lag behind live grew to 5.1 s. `demuxer-cache-time - time-pos` peaked at **1.03 s**, because the demuxer stops at about 1 s of readahead and TCP backpressure holds the rest. So H264View's `buffer - position > 2 s` check is never true and the seek never runs. After resume, `untimed=yes` worked through the backlog and the lag settled at about 1.2 s.
- **Stall plus seek (c):** an unconditional seek to `demuxer-cache-time` on resume could jump at most about 1 s.

The watchdog as written does nothing under `cache=no`, so it is turned off.

## Recommendation

- Offer H.264 on macOS. Also offer it on Android, which is untested but allowed by the rule below once macOS passes. The H264View error fallback to MJPEG covers a platform where it fails.
- Leave the catch-up seek off.
- Re-run the plan's GUI spike against the phone when it is reachable with screen sharing on, to measure real end-to-end latency and confirm Android.

H264_PLATFORMS: macos,android
